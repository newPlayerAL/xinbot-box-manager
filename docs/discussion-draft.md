# XinBot Box Manager 前期方案讨论稿

> 文档状态：讨论稿，未确认。
>
> 本文用于保存当前交流中形成的想法和假设，不是需求规格、架构决策记录或开发承诺。
> 除非后续明确确认，否则其中的功能、技术选型、资源参数和优先级都可以调整。

## 1. 背景与目标场景

目前设想的运行环境是一台无头迷你主机：

- 日常管理只能通过浏览器完成；
- 同时运行约 1～3 个 XinBot 实例；
- 主要用途是 BackToTheBase（BTTB）或消息响应；
- 候选 SoC 包括 Allwinner H618 和 Rockchip RK3518；
- 设备可能只有 2 GB 内存，因此需要控制常驻服务和单实例开销；
- 希望统一完成实例、配置、插件、日志和运行状态管理。

当前目标不是托管大量实例，也不是在设备本地提供桌面 GUI。

## 2. 现有项目的初步理解

### XinManager

目前看到的 XinManager 更偏向 XinBot 的网页观察和远程交互界面，例如远程终端、
状态展示以及世界/3D 查看。它依赖 XinBot 侧提供远程数据，暂未看到完整承担以下职责：

- 创建和删除实例；
- 安装、启动、停止和重启 XinBot 进程；
- 管理 Java 运行环境；
- 为不同实例维护独立配置和插件；
- 设置开机启动、异常拉起和资源限制。

因此，直接把现有 XinManager 当作无头设备的完整控制平面，可能不完全适合当前场景。
这一判断仍需在确定复用方案前再次核对其最新代码和接口。

### xinbot-gui-win

`xinbot-gui-win` 已经包含不少本地实例管理能力和可参考的业务规则，例如：

- 实例启动和停止；
- Java 与 XinBot 运行参数组织；
- 配置文件生成；
- 官方插件目录及依赖处理；
- 日志和控制台交互；
- 多实例工作目录管理。

它面向 Windows 桌面和 Tauri 应用，不能原样作为无头 Linux 网页管理端使用，但其中的
领域模型、参数校验、插件目录以及部分后端逻辑可能可以复用或迁移。

## 3. 候选产品方向

### 方向 A：单一的统一管理端

一个常驻后端同时提供管理 API、实时日志通道和静态网页，并直接管理各 XinBot 子进程。

可能的优点：

- 浏览器只需要访问一个地址和端口；
- 认证、配置和实例状态只有一套来源；
- 减少重复常驻服务，更适合 2 GB 设备；
- 可以统一处理进程退出、自动重启、资源限制和升级；
- 后续仍可按需接入 XinRemote 的玩家、世界和物品信息。

需要付出的成本：

- 需要重新整理管理端的后端边界；
- 不能直接照搬桌面端的 Tauri 接口；
- 如果复用 XinManager 页面，需要适配新的 API 和认证方式。

当前讨论更倾向这个方向，但尚未确认。

按照目前对第一版的设想，“统一”首先是指用一个网页服务完成基础实例管理，并不表示
第一版就要吸收 XinManager 或 XinRemote 的能力。

### 方向 B：新建进程管理功能，旁挂独立 XinManager

新服务只管理安装、配置和进程；现有 XinManager 继续提供远程观察与交互。

可能的优点是早期改动较少，两个项目的责任边界看起来比较直接。潜在问题包括：

- 用户可能需要访问两个网页或端口；
- 两套认证、配置和实例映射容易产生不一致；
- 部署、更新和故障排查更复杂；
- Node/Web 服务等重复常驻开销对 2 GB 设备不够友好。

该方向暂不排除，但目前不是优先倾向。

## 4. 第一版范围与后续功能池

### 第一版的当前设想

第一版倾向先实现一个“浏览器版 `xinbot-gui-win`”：保留无头设备实际需要的基础管理
能力，把运行链路做通和做稳，不引入 XinManager 及其高级功能。

当前考虑纳入第一版的能力包括：

- 浏览、创建、编辑和删除 XinBot 实例；
- 启动、停止和重启实例；
- 维护每个实例的 XinBot 配置；
- 选择和配置 DirectConnect、BTTB、MovementSync 等插件；
- 查看实时控制台和历史日志，并发送控制台命令；
- 展示实例的基础运行状态和资源占用；
- 为每个实例维护相互隔离的工作目录；
- 处理启动失败、进程退出和必要的错误提示；
- 提供最简的管理账号、密码和登录会话管理；
- 通过浏览器完成以上操作。

当前明确倾向不放入第一版的内容包括：

- 集成或附带运行 XinManager；
- 集成 XinRemote；
- 世界、区块或 3D 地图查看；
- 背包、玩家等高级远程观察能力；
- 为上述高级能力提前建立复杂的数据链路；
- 复用或改造 XinManager 前端页面。

这样可以先验证多实例生命周期、配置和插件管理、ARM 兼容性以及 2 GB 设备上的长期
稳定性。等基础版本稳定后，再决定是否需要 XinManager 类能力，以及应该内置、插件化
还是作为独立服务提供。

以上仍是当前倾向，具体哪些基础功能属于第一版还没有逐项确认。

### 基础功能候选细目

#### 基础管理

- 创建、复制、编辑和删除实例；
- 启动、停止和重启实例；
- 展示运行状态、在线状态、运行时间、PID、CPU 和内存占用；
- 查看实时日志并向实例控制台发送命令；
- 设置开机自启、异常自动拉起和重启退避；
- 防止多个启动请求重复拉起同一个实例。

#### 配置与插件

- 通过表单维护常用 XinBot 配置；
- 在需要时允许查看或编辑原始配置；
- 管理 DirectConnect、BTTB、MovementSync 等插件；
- 校验插件依赖和兼容性；
- 为各实例使用隔离的工作目录、配置和日志；
- 导入、导出或备份实例。

#### 网页访问

- 一个入口管理全部实例；
- 实时日志和状态可考虑使用 WebSocket 或 SSE；
- 提供基础登录认证；
- 前端可以构建为静态资源，由管理后端直接提供；
- 暂不默认假设设备会直接暴露在公网。

#### 最简账号与密码管理

第一版可以只考虑一个本机管理员账号，不引入完整的用户系统。候选的最小范围是：

- 首次使用时设置管理员账号和密码，不内置通用默认密码；
- 使用账号和密码登录；
- 主动退出登录；
- 登录后修改管理员账号和密码；
- 会话在一段时间后过期，具体时长待定；
- 密码仅保存带随机盐的安全哈希，不保存或记录明文；
- 登录接口具有基础的失败限速，避免无限尝试；
- 实时日志、WebSocket/SSE 和所有管理 API 使用同一登录状态；
- 遗忘密码时，通过 Linux 控制台命令重置管理员密码。

遗忘密码恢复当前可以考虑采用类似下面的命令形式，最终名称和参数尚未确认：

```shell
sudo xinbot-box-manager admin reset-password
```

该命令的候选行为是：

- 只允许 root 或获得明确授权的本机系统用户执行；
- 在终端中交互式输入并确认新密码，不接受把明文密码直接放在命令行参数中；
- 不在 shell 历史、进程列表或日志中记录密码；
- 使用与网页设置密码相同的安全哈希方式保存新密码；
- 重置成功后使现有网页登录会话全部失效；
- 记录发生过本机密码重置，但审计记录不包含密码内容。

这种方式不提供网页上的“忘记密码”入口。恢复权限以能够登录 Linux 控制台、SSH，或
以其他方式取得设备的系统管理权限为前提。

当前倾向不在第一版实现：

- 自助注册；
- 多管理员和普通用户；
- 角色与细粒度权限；
- OAuth、LDAP、短信或邮件验证；
- 云端账号和跨设备账号同步。

账号认证只能阻止未登录访问，不能替代传输加密。如果设备可能经过不可信网络访问，
仍需确定由管理端直接支持 HTTPS，还是要求通过可信反向代理或 VPN 接入。

### 后续可选的远程观察能力

- 玩家和连接状态；
- 背包或物品信息；
- 世界/区块/3D 查看；
- 与机器人有关的远程操作。

这些能力不在当前设想的第一版范围内。以后如果确有需求，可以借鉴 XinManager，但应
按需加载。对于只运行 BTTB 或消息响应的设备，不应因为未使用的 3D/世界查看功能而
长期保留大量数据。

## 5. 候选技术形态

目前讨论过的形态是：

```text
浏览器
   │ HTTP + 实时事件
   ▼
统一管理服务
   ├── 实例/配置/插件管理
   ├── 日志与控制台代理
   ├── 认证和管理 API
   └── 静态网页
          │
          ├── XinBot 实例 1
          ├── XinBot 实例 2
          └── XinBot 实例 3
```

管理服务可以考虑使用 Rust，以便复用 `xinbot-gui-win` 的部分经验并控制常驻开销；
但语言、Web 框架、前端框架、数据存储和进程托管方式均未确认。

XinRemote 不在当前设想的第一版范围内。如果后续使用，它更适合作为 XinBot 运行数据
接口，而不是承担操作系统进程管理。

## 6. 内存讨论与初步测量

“2 GB 不适合”目前没有足够依据。针对 1～3 个轻量实例，2 GB 应继续作为候选配置。

在当前开发机上，使用现有 XinBot 2.5.0 构建进行了一次短时间、未连接真实服务器的
基线测试：

| 场景 | Java 堆使用 | 进程 RSS |
| --- | ---: | ---: |
| Core + DirectConnect | 约 22 MB | 约 133～141 MB |
| 再加载 BTTB + MovementSync | 约 12～26 MB | 约 139～145 MB |

这只能证明插件加载和空闲重连时没有明显的大内存需求，不能替代真实负载测试。登录真实
服务器后，协议缓冲、区块、实体、玩家和插件状态会继续占用内存；不同 JVM、ARM64 平台
和运行时间也会影响结果。

当前 `xinbot-gui-win` 启动 XinBot 时没有显式设置 `-Xms`/`-Xmx`。模拟主机拥有 2 GB
内存时，Java 默认给单个实例计算出的最大堆约为 512 MB。最大堆不是已经占用的内存，
但三个不受约束的 JVM 在峰值时可能竞争内存。

可以考虑但尚未确认的初始参数：

- BTTB/消息响应实例：`-Xms32m -Xmx256m`；
- 活动区块较多、移动或远程查看实例：`-Xms64m -Xmx384m`；
- 每实例再使用 cgroup/systemd 设置总内存保护上限；
- 配置 zram 作为应急缓冲，不把存储设备上的 swap 当作正常运行内存；
- 错开多个实例的启动和重连，降低瞬时 CPU 与内存峰值。

现阶段较合适的表述是：2 GB 可能足以支持 1～3 个轻量实例；4 GB 提供更宽松的余量，
但不应在没有实机数据时被定义为最低配置。

## 7. SoC 与设备方面的待验证项

H618 和 RK3518 都是当前候选，尚未选择。除了纸面 CPU 参数，还需要验证具体板卡：

- 64 位 Linux 镜像和 Java 21 ARM64 的稳定性；
- 内核、以太网、eMMC、温控和看门狗支持；
- 三实例同时登录、重连、寻路时的 CPU 峰值；
- 长时间运行后的温度、降频和断网恢复；
- 2 GB 机型的实际可用内存，而不只是标称容量；
- eMMC 与 SD 卡在日志、更新和断电场景下的可靠性；
- 设备厂商对系统镜像和内核的维护情况。

对于这一负载，常态内存未必是首要瓶颈；多实例同时登录、协议初始化和寻路时的单核性能
及温控也可能决定体验。

## 8. 建议的验证方式

在确定最低硬件配置前，可以为两个候选平台做同一套测试：

1. 使用接近量产的系统镜像和 Java 版本；
2. 分别运行 1、2、3 个真实 XinBot 实例；
3. 覆盖空闲、消息响应、BTTB、断线重连和短时寻路；
4. 连续运行至少 24～48 小时；
5. 记录每实例及整机的 RSS、Java 堆、CPU、温度、降频、网络和重启次数；
6. 检查内存是否持续增长，以及系统进入 zram/OOM 后能否正确恢复；
7. 根据实测结果再确定 JVM 上限、并发启动策略和最低内存。

## 9. 尚未决定的问题

- 首个版本必须包含哪些功能；
- 基础版本完成后是否需要 XinManager 类能力；
- 如果需要，是否复用 XinManager 的前端组件，以及复用到什么程度；
- 是否从 `xinbot-gui-win` 抽取共享核心库；
- 后端和前端的具体技术栈；
- 进程由管理服务直接托管，还是为每实例生成 systemd unit；
- 配置保存格式和敏感信息保护方式；
- 首次设置管理员账号的流程；
- Linux 控制台密码重置命令的最终名称、授权方式和运行时交互；
- 登录会话有效期、Cookie 策略和登录失败限速参数；
- 局域网访问、反向代理、HTTPS 和公网访问的边界；
- 后续是否需要增加普通用户、只读用户和角色权限；
- 更新、回滚、备份和恢复机制；
- 2 GB 是否作为正式支持配置；
- 最终采用 H618、RK3518，还是保留多个硬件版本；
- 产品名称、仓库名称和发布名称是否最终都使用 XinBot Box Manager。
